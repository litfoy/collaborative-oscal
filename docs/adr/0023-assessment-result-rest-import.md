# ADR 0023: REST Import for Native OSCAL Assessment Results

- Status: Accepted
- Date: 2026-11-19

## Context

Assessment Results already support tenant-scoped working drafts, immutable publication snapshots, pinned Assessment Plan context, and OSCAL 1.2.1 export validation. External assessment automation now needs to submit native OSCAL Assessment Results JSON into the same domain lifecycle without introducing separate machine-identity infrastructure or a parallel aggregate model.

## Decision

- Add authenticated tenant-scoped REST import endpoint:
  - `POST /api/v1/tenants/{tenant_id}/assessment-plans/{plan_id}/versions/{version_id}/assessment-results/import`
- Accept native OSCAL Assessment Results JSON 1.2.1 without proprietary request envelope.
- Reuse existing OSCAL validation stack, tenant authorization, and Assessment Results domain/persistence workflow.
- Implement strict reverse mapping of the currently supported authoring subset generated by draft export, into existing Assessment Results working-state fields.
- Require exactly one native `results` entry.
- Reject unsupported fields and incompatible values instead of silently dropping information.
- Enforce `import-ap.href` equivalence with the selected Assessment Plan version export path (`_plan_href` convention).
- Create a new Assessment Results aggregate atomically with `concurrency_version = 1`; do not auto-publish.
- Preserve imported observation/finding/evidence UUIDs in working state.
- Preserve source provenance on the aggregate:
  - source OSCAL document UUID,
  - source result UUID,
  - source metadata version,
  - source metadata last-modified,
  - submitting authenticated principal,
  - import timestamp.
- Preserve existing internal aggregate identity and publication identity conventions.
- Use tenant-scoped idempotency identity keyed by source OSCAL document UUID with canonical JSON digest matching independent of formatting and object-member order.

## Idempotency contract

- First successful submission: HTTP `201` with `AssessmentResultResponse`.
- Identical replay: HTTP `200` returning existing aggregate.
- Same source document UUID with different content or Assessment Plan context: HTTP `409` (`detail.code = import_conflict`).

Implementation uses transaction-safe duplicate detection backed by a tenant-scoped unique index on non-null source document UUID and conflict-aware retry handling for concurrent submissions.

## Consequences

- Human-authored and automation-authored assessment results share the same aggregate, optimistic concurrency behavior, and publication/export lifecycle.
- Existing Assessment Results and immutable snapshots remain unchanged.
- Import is intentionally constrained to a validated subset aligned with current authoring/export support; broader OSCAL import remains out of scope.
